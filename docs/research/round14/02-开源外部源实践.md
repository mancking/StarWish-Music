## 二、可借鉴机制清单（按落地优先级）

### M1. 首次启动：无源可用时的「框架内容 + 引导范式」
- **开源实现要点**：
  - lx-music：协议闸门倒计时（`PactModal.vue:60`）→ 搜索页空态只有欢迎语，**没有源导入引导（这是反面教训）**；源初始化失败弹错误框（`useInitUserApi.ts:133-141`）。
  - MusicFree：**NO_PLUGIN专用空态组件**——检测到零插件时整个搜索页切换为 `NoPlugin` 引导页（`useSearch.ts:38-41` + `searchPage/index.tsx:44-46`），用户被显式告知「你还没有音源」。
  - musicxx：插件框架缺失时**主程序照常启动**，功能降级而非崩溃（README）。
- **星河适配建议**：首启不阻塞、框架内容（本地音乐/示例歌单/内置演示源）立即可用；当外部源为空时，在搜索/首页给**NO_SOURCE级别的引导空态**（「导入第一个音源」按钮直达导入弹窗），而不是像落雪那样只留一个欢迎语。保留本地可用内容作为「框架内容可用」基线。
- **次生问题**：引导空态要区分「零源」「有源但全部加载失败」「有源但当前选中源失败」三种状态，文案与跳转不同；协议/法律边界（源返回URL不校验内容真实性）应像落雪一样写入首次协议弹窗（`PactModal.vue:11`）。

### M2. 导入→生效→持久化完整链路（含事件/重载边界）
- **开源实现要点**：
  - 校验三件套：URL格式（https?）+ 脚本头部契约（落雪JSDoc块注释 `utils.ts:81-89`）+ 体积上限（落雪9MB `UserApiOnlineImportModal.vue:72`；any-listen逐字段长度上限 `resource.ts:211-217`）。
  - 落雪：导入成功 → 压缩存储（gz_前缀）→ 立即作为可选项出现；**切换激活源 = 销毁旧沙箱窗口+清缓存+建新窗口**（`main.ts:134-144`），进行中请求以 `source changed` 取消（`useInitUserApi.ts:10-20`）。
  - MusicFree：新插件文件落盘后 `setPlugins` 通知UI；重复hash静默成功、降级拒装（`index.ts:200-230`）。
  - any-listen：**事务式更新=备份→替换→失败回滚**（`manage.ts:178-198`）；更新后自动重启扩展（`manage.ts:193`）。
- **星河适配建议**：导入链路 = 输入URL/选文件 → fetch(follow_max≤3) → 校验契约（头部magic/字段白名单/体积上限）→ 沙箱冒烟（跑一次search探活）→ 持久化（压缩/落盘）→ 发 `source-added` 事件刷新源列表；激活源切换时取消在途请求，避免「切换后旧源回调污染新UI」。更新用 any-listen 的备份-回滚模式，禁止「写坏了直接覆盖旧源」。
- **次生问题**：导入失败要给可操作原因（网络404→「源地址不存在，请联系作者」MusicFree `index.ts:361-366`；解析失败→「无效的源文件，检查格式」），不要只弹「导入失败」；沙箱冒烟失败应允许保留已导入条目但标记「初始化失败」，给用户重试/删除入口。

### M3. 多源冗余策略（优先级/自动切换/健康度）
- **开源实现要点**：
  - 落雪播放换源：**顺序试换**（shift逐个）+ 已试源黑名单（retryedSource）+ **429熔断立即停手** + 15s跨源搜索超时 + UI回调告知「正在切换到其他来源」（`core/music/utils.ts:56-59,254-262,282,317`）。
  - MusicFree：用户可显式指定**某平台的替代插件**（`meta.ts:119-129` + `plugin.ts:247-252`）——人工配置的兜底，而非自动探测。
  - 落雪搜索：跨平台并行、单源失败返回空不拖垮整体、结果去重+相似度重排（`search/music/action.ts:91-111`）。
  - MusicFree搜索：每插件独立状态机，失败插件标记ERROR，其他继续（`useSearch.ts:153-179`）。
- **星河适配建议**：①搜索=全启用源并行，单源失败降级为空结果；②播放=首选源失败→顺序试备用源，已试源不重试，遇429/熔断错误立即停手不轰炸；③保留「换源」手动入口（落雪 `toggle_source_try: "尝试切换到其他来源..."` `zh-cn.json:720`）；④可选：用户级「指定某平台兜底源」配置（MusicFree替代插件）。
- **次生问题**：换源后播放的歌曲meta（封面/歌词）与实际URL来源不一致，需在UI标注「实际来源：XX」；自动换源不要陷入死循环——retryedSource黑名单必须贯穿整次播放解析。

### M4. 订阅源定时刷新（周期/网络策略/手动兜底）
- **开源实现要点**：
  - **MusicFree 24h静默自动更新**：启动时检查 `pluginUpdateTime`，距上次>86400000ms才遍历启用插件重新拉各自srcUrl，失败静默catch（`bootstrap.ts:206-224`）——**周期长、启动时跑、不打断用户、失败无感**。
  - **any-listen 商店版本比对**：启动拉一次market list，compareVersions 生成红点更新提示（`onlineList.ts:94-107,191-201`）；**源码自认定时刷新未做（TODO注释 `onlineList.ts:194`）**——即成熟如any-listen，定时市场刷新也是未完成项。
  - 落雪：完全无主动刷新，靠插件自报+用户手动（`preload.js:253-257`）。
  - 手动兜底：MusicFree「更新全部」按钮（`pluginList.tsx:218`）；any-listen skipCache强制刷新（`onlineList.ts:125`）。
- **星河适配建议**：采用 MusicFree 模式——启动时后台静默检查（距上次>24h），逐个源重新拉取其自报更新URL，有新版本只做红点提示不自动覆盖；设置页提供「立即检查更新」手动按钮；订阅源列表（市场manifest）拉取失败静默降级用缓存。
- **次生问题**：自动更新必须走 M2 的事务式替换（备份-回滚），否则一次源站坏更新会把用户打到无声；更新检查不要并发轰炸——串行或限并发，源站大多是个人VPS。

### M5. 视频源插件化抽象
- **开源实现要点**：
  - MusicFree bilibili插件 = 视频平台适配音乐模型的完整先例：视频当album、分P当track（`plugins/bilibili/index.ts:165-172,683-707`）；DASH接口 `fnval:16` 抽 `dash.audio[]` 按带宽映射音质档位（`:380-404`）；无DASH回退flv durl（`:406`）；**播放headers透传**（referer/host伪装，`:409-426`）。
  - SupportMediaType 没有video类型（`types/common.d.ts:3-8`）——即「视频源」在插件层不做新资源类型，复用音乐CRUD。
  - 落雪协议文本：客户端不校验源返回URL的内容真实性（`PactModal.vue:11`）——视频音频同源取流的法律免责已被先例验证。
- **星河适配建议**：视频外部源第一版**不引入独立video资源类型**，直接复用音乐源契约（search→music列表、getUrl→音频流URL）；视频平台插件内部自行完成DASH抽音频；播放器侧支持 `{url, headers}` 透传（ExoPlayer/VideoView 都支持自定义请求头），否则B站类源全部不可播。后续若需要视频画面，再在插件契约加可选 `getVideoUrl` 扩展字段，保持音乐流为主。
- **次生问题**：DASH音频流是无容器m4s片段，普通播放器直接播会失败——星河播放器需支持 HE-AAC/m4s 直解或让插件返回合并后的可播URL；视频源的封面图/时长/歌词为空要做UI降级。

## 三、反模式提醒（踩坑清单）

1. **订阅源/市场地址硬编码无镜像兜底**：落雪源仓库README专门列了6个ghproxy备用域名（`lx-source/README.md:94-105`），因为GitHub raw在国内不稳定；any-listen把镜像hosts做成配置项 `extension.ghMirrorHosts`（`docs/docker-server_zh.md:39`）。**星河若硬编码单一raw地址，首次启动导入流程在国内大概率直接失败**——导入URL输入框旁应提供「加速地址」说明，客户端内建镜像回退列表。
2. **导入校验缺失**：不校验脚本头部契约 → 坏脚本落库后每次启动沙箱崩溃，用户不知为何无声。落雪的「必须有块注释+JSDoc字段」（`utils.ts:81-89`）和any-listen的全字段返回值校验（`resource.ts`）是正反两面：**导入时校验+运行时返回值再校验，两道都要有**。
3. **市场/更新无版本比对，盲目覆盖**：MusicFree的降级保护（已装更新版本则拒，`index.ts:212-230`）说明「重新拉一次就覆盖」是危险默认——一次源站回滚发布会把用户源打旧。更新必须compareVersions + 事务回滚。
4. **沙箱不严=系统风险**：落雪在导入弹窗里明文警告「导入包含恶意行为的脚本仍可能会影响你的系统，请谨慎导入」（`zh-cn.json:738`），并把每源塞进独立无节点能力的BrowserWindow（`main.ts:74-123`）。musicxx动态库插件「无沙箱、崩溃=主崩、权限仅展示」（`plugin-guide.md:163`）是反例——星河若走JS插件路线，必须真隔离（独立线程/VM/禁网络外的系统调用），不要学无沙箱动态库路线。
5. **首次启动无引导，用户面对空白**：落雪搜索页空态无导入引导（`BlankView.vue:19-21`），新用户不知道为什么搜不出歌。应学MusicFree的NO_PLUGIN专用空态（`useSearch.ts:38-41`）。
6. **切换源不取消在途请求**：会出现「切到新源后旧源的搜索结果刷了新UI」的串台bug——落雪的watch reject模式（`useInitUserApi.ts:10-20`）必须照搬。
7. **429/限流不熔断**：换源逻辑遇限流仍顺序试完全部备用源，等于把所有源都打一遍429——落雪 `err.message == tooManyRequests 立即抛错`（`utils.ts:282,317`）是正确熔断姿势。
8. **更新检查频率过高**：MusicFree定24h且启动静默跑（`bootstrap.ts:212`）；星河不要做每次启动或每小时轮询——个人源站带宽扛不住，且市场manifest刷新是用户感知为「卡」的首要来源。
9. **深度链接/文件关联缺失**：MusicFree支持 `musicfree://install/` scheme与打开.js即装（`bootstrap.ts:229-256`），降低分享门槛；星河若要社区传播插件源，URI scheme是标配而非加分项。
