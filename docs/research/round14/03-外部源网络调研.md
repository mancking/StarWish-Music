### 对星河音乐的启示（外部源体系选型）
- **主流成熟路径 = 清单订阅制**：`plugins.json`/`plugins.yaml` 一个 URL → 客户端拉取清单 → 用户勾选安装 → 记录已装插件的 URL+version。LX 用单脚本 .js，MusicFree 用清单 JSON，二者都提供"本地文件导入"和"在线 URL 导入"双通道。
- **版本检测**：清单里带 `version` 字段，客户端比对已装插件版本号即可判断更新；LX 还额外允许脚本主动 `updateAlert` 弹窗引导更新。
- **合规红线**：MusicFree 官方仓库收到告知函后直接下架国内厂商音源；LX 被投诉后移除全部内置源。→ 星河应从 v1 起就**不内置任何平台音源**，音源全部用户自导入，且内置的只是"框架播放器"。

### 落到星河的首次启动设计建议
1. **0~1 屏引导 + 空态即引导**：参考 Material FTU 范式——首屏不做花哨教程，空态页直接 = 问候文案 + 一句"添加第一个音源/导入歌单"的主 CTA（1 屏内完成），不做 3 屏以上滑动引导。
2. **无源也可用**：内置"框架内容"作为零数据期的填充——例如内置一个本地音乐扫描入口 + 一个示例歌单/说明页，避免打开全空白（网易云"推荐填充"思路）。
3. **延迟权限/网络请求**：权限请求推迟到对应功能真正用到时（digia 的结论：过早要权限是第一流失点）。
4. **埋点目标**：引导完成率 ≥70%、首会话激活（完成一次播放）率对标 30~50%。

### 对星河的订阅刷新建议
1. **周期**：插件/音源清单类元数据刷新——启动时检查一次（MusicFree 模式，成本最低、合规友好）；歌单/榜单内容类——默认 30~60 分钟一次（Apple/FreshRSS 区间），单源最低不低于 15 分钟（FreshRSS 生态礼貌下限）。
2. **网络策略**：
   - 启动时 + 手动下拉刷新为第一优先；
   - 同域名请求错峰 ≥2s、并发 ≤3~5（feedr + MusicFree 网络优化建议）；
   - 错过周期的源优先补拉（Microsoft Feed 排队策略）；
   - 可配置 `next_fetch_at` 队列模型（0xkishan），支持分批 `maxFeeds`（FreshRSS 模式）避免一次性打爆源站。
3. **手动兜底**：每个订阅源保留"立即更新"按钮；更新前提示"将覆盖本地列表"（LX 文案已验证此警告必要）。
4. **事件驱动补充**：条件成熟时支持 WebSub/WebHook 式推送，降低轮询成本（FreshRSS 路线）。

### 对星河音乐（音视频分离架构）的启示
1. **视频源 = 一类特殊音源插件**：协议上只需 `getMediaSource` 返回音频流 URL（可从视频流中抽取/转码），与普通音源同接口——星河的"音视频分离"架构可直接复用音源插件通道承载 bilibili/YouTube 类源，无需另起一套。
2. **参考 MusicFree 的能力分级**：`search/getMediaSource/getLyric` 最小集即可跑通"搜 B 站视频→播音频轨"；封面/专辑信息可后补。
3. **合规提示**：官方源仓库对视频类相对宽容（bilibili/youtube 至今保留），下架风险集中在"国内音乐厂商官方接口"。星河内置示例源池时可优先考虑视频站/私有服务器/WebDAV 类，规避音乐版权雷区。
4. **版本与失效**：bilibili 插件版本号 v0.2.3 远高于其他（0.0.x），说明视频源接口变动频繁——星河的清单订阅 + 版本比对机制必须默认开启，且单源失效不应拖垮全局搜索（参考 Listen1"自动切换失效播放源"、MusicFree"异常插件清除、冲突插件检测"的插件管理设计）。
