### Bug75｜`storage/db.ts:21` 历史写入 channel 名仍为 `'history:add'`，两端 handler 注册的是 `'db:history:add'`（round9 C-04 未落地）

### Bug77｜`mobile/player.ts load()` 无 loadToken，切歌/换音质时旧 resolveUrl 回调覆盖新 src（round8 Bug54 未落地）

- 证据：
  - `src/mobile/player.ts:117-126` `await resolveUrl(...)` 之后仅靠 `if (index !== i) return`（:119）判断是否切歌。
  - `src/mobile/player.ts:348-354` `setQuality()` 直接 `void load(index, true)`——同一 index，:119 的 guard 永远不成立，**快速连切两次音质时旧音质的 resolveUrl 后返回**，`el.src` 被旧 URL 覆盖（:125），最终播放的是旧 flac 流。
- 影响：弱网/高延迟取链下，用户点 320k → flac → 320k，最终可能仍播第一条 flac 流，UI 上品质标签却已是 320k。

### Bug78｜`mobile/player.ts` catch 与 error 事件双重 retryCount++，一次失败直接跳到 MAX_RETRY（round8 Bug46 未落地）

- 证据：
  - `src/mobile/player.ts:130-148`（load catch）：:140 `markSourceFailed(song)`，:142-145 `retryCount++; void load(i, autoplay, true)`。
  - `src/mobile/player.ts:210-220`（el 'error' 监听）：:213 `markSourceFailed(song)`，:214-217 `retryCount++; void load(index, true, true)`。
  - 媒体元素失败时：el 触发 error 事件（同步/微任务），随后 `await el.play()` 的 reject 进入 catch——**两条路径都会执行 markSourceFailed + retryCount++**，一次失败 retryCount 直接到 2 = MAX_RETRY(2)，下一次失败直接 `failCurrent` 跳下一首。
- 影响：弱网/死链时"换源重试 2 次"被压缩成"一次失败即跳歌"，用户感知连播多首都失败。
- 解决方案：catch 与 error 事件加互斥标记（模块级 `let errorHandled=false`，catch 开头置 true、error 开头检查并在 load 入口 reset）；或统一由 error 事件驱动重试，catch 仅处理 :133 notallowed 分支直接 return。
- 适用端：移动。

### Bug79｜`mobile/player.ts` `await resolveUrl()` 无外层超时，弱网/半开 TCP 时 status 永卡 loading（round8 Bug49 未落地）

- 证据：`src/mobile/player.ts:118` 直接 `await resolveUrl(song, ...)`，外层没有 Promise.race 超时；resolveUrl 内部走 `electron/core/music-service` 的 fetch 链，对端不响应时永不 reject。
- 影响：弱网下 status 卡 `'loading'` 数分钟，切歌/暂停按钮看似无响应；旧 await 链恢复后还会反过来 publish 一次旧状态。
- 解决方案：`await Promise.race([resolveUrl(...), new Promise((_,r)=>setTimeout(()=>r(new Error('取链超时')), 10000))])`，超时走 `markSourceFailed` + 换源/跳下一首。
- 适用端：移动。

## 二、本轮新发现的逻辑问题

### Bug87｜`mobile/player.ts` error 事件处理器不校验当前 index，快速切歌时旧 src 的 error 会污染新曲

- 证据：`src/mobile/player.ts:210-220`：
  ```
  el.addEventListener('error', () => {
    if (!el.src) return
    const song = state().song
    markSourceFailed(song)
    if (retryCount < MAX_RETRY) { retryCount++; void load(index, true, true); return }
    failCurrent(song, '音频加载失败，可能链接已失效')
  })
  ```
  用户快速从 A 切到 B 时：A 的 src 被清掉/替换为 B 的 URL 之前，A 的 error 事件可能滞后触发。此时 `el.src` 是 B 的新 URL（已被 load 设置），`state().song` 是 B，但代码对 `index` 上的"当前曲"做 retryCount++ + 换源，**B 刚起播就被打一次失败标记**，后续 B 真出错时 retryCount 已被 A 消耗。
- 影响：快速切歌场景下，新曲被错误加入 failedSources，可能被自动跳过，用户感知"点了这首歌不播，直接跳了下一首"。
- 解决方案：error 事件里 `const i = index` 取快照，配合 Bug77 的 loadToken：`if (loadToken !== tokenAtError) return`；或 error 处理器只在 `el.src` 仍对应当前 song.source 时才处理。
- 适用端：移动。

### Bug88｜`mobile/player.ts` 重复绑定两次 `'playing'` 事件，publish 与 updateMediaSession 各跑两次

- 证据：
  - `src/mobile/player.ts:197-205` 第一次：`status='playing'; error=null; retryCount=0; consecutiveFails=0; startTick(); publish(); updateMediaSession()`。
  - `src/mobile/player.ts:221-228` 第二次：`const song = state().song; if (song && histMarked !== song.id) { histMarked = song.id; addHistory(song, 0) }`。
  - 同一媒体元素的 playing 事件**两个监听器都执行**：publish() 与 updateMediaSession() 被调用两次（第二次 publish 由 :197 的第一次监听器触发，但 history 写入在 :221 独立监听器；updateMediaSession 在 :197 末尾调一次，:204 又调一次）。
- 影响：每次起播 `emit('player:state')` 广播两次、MediaSession metadata 被设置两次，锁屏面板可能闪一下；histMarked 写入本身 OK，但与第一次监听器的并发顺序无保证。
- 解决方案：把 :221-228 的 history 写入合并进 :197-205 的监听器，删掉第二次 addEventListener('playing', ...)。
- 适用端：移动。

### Bug89｜`stores/player.ts onSongChanged` 歌词失败后每次 player:state 广播都重新请求歌词

- 证据：
  - `src/stores/player.ts:159-161`：`const same = s.id === lastSongId; if (same && (lyricLoading.value || (lyric.value && lyric.value.lines.length))) return`。
  - 歌词首次请求失败（如该曲无歌词、网络错）后：`lyric.value = null`（:189 catch 内）、`lyricLoading.value = false`（:191 finally）。

- 影响：一首无歌词的歌播放期间，每 500ms 触发一次歌词 IPC + 封面回退请求，主进程反复查库/发网络请求，浪费资源且可能导致 LyricsPane 闪烁。

### Bug92｜`electron/core/download.ts streamTo` 与 reader.read() 无超时，网络 stall 任务永远 running

- 证据：
  - `electron/core/download.ts:147-173` `streamTo` 内 `await fetch(url, ...)` 无超时，`:163 for(;;) { const {done,value} = await reader.read() ... }` 无 stall 检测。

### Bug95｜`useVideoGestures.ts onTouchMove` 每次高频 getBoundingClientRect() 引发同步 layout

- 证据：
  - `src/player-video/useVideoGestures.ts:95-96` 在 `onTouchMove` 内 `const box = (e.currentTarget as HTMLElement).getBoundingClientRect()`，而 `onTouchStart` :69 已经取过一次存到 `g.w`/`g.h`（但没存 box.left）。
  - :96 用 `box.left` 判左/右半屏。
- 影响：touchmove 以 60Hz 触发，每次强制 layout flush，低端机手势跟手性差、掉帧。
- 解决方案：onTouchStart 时缓存 `g.left = box.left; g.width = box.width`，touchMove 用缓存值；仅在 resize/rotate 时刷新。
- 适用端：移动 + 平板。

### Bug96｜`electron/core/media.ts:495-507` 音频 chunks 数组整曲驻留内存，播完才 concat 写盘

- 证据：`electron/core/media.ts:495 const chunks: Buffer[] = []`，:506 `if (value) chunks.push(Buffer.from(value))`，:502 done 时 `Buffer.concat(chunks)` 一次性写盘。一首 30MB FLAC 全程 chunks 驻留，多首连续播放时旧 Buffer 需等 GC 回收。
- 影响：长时间播放/无损音质下内存峰值飙升，低端机/老机器 OOM 或 swap。
- 解决方案：改为边收边写 .part 文件（与视频缓存同路径），done 时 rename；写盘失败不影响播放（透传 body 已经 enqueue 给客户端）。
- 适用端：桌面。
