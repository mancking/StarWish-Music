## 一、社区聚合仓库 / 镜像候选清单（默认收录候选）

合规评级口径：
- **高风险**：仓库内容直接提供国内音乐厂商（网易云 / QQ / 酷狗 / 酷我 / 咪咕等）的在线播放 / 下载取链能力，或其历史已被权利人投诉 / 发告知函。
- **中风险**：内容偏中立（自建服务器接口、开源音频站、翻唱平台、本地协议），但作者 / 仓库归属不稳定，可能随时被 fork 改向或失效。
- **低风险**：官方 / 半官方示例仓，已主动剥离国内厂商源，或仅承载协议 / 工具链，不承载侵权内容。

## 二、协议生态横评

| 维度 | lx 协议（落雪 / LX Music） | MusicFree 插件 | listen1-api / any-listen | 视频源插件（B站 / YouTube） |
|---|---|---|---|---|
| 分发形态 | 单个 `.js` 脚本（UTF-8，ES6+），头部注释元信息 `@name/@description/@version/@author/@homepage` | `.js` 插件文件或 `.json` 描述文件；清单式市场（`plugins.json` / `registry.json`），每条目含 `name/url/version` | 编译进 App（listen1）或服务端配置（any-listen） | 作为 MusicFree 插件 / lx 脚本的一种源类型存在 |
| 初始化 | 脚本执行后必须 `send(EVENT_NAMES.inited, { sources, openDevTools })` 声明支持的源与 actions；初始化阶段任何错误即视为初始化失败【亲自精读】 | 插件导出对象 / 接口约定（`plugin.d.ts`：search、musicUrl、lyric 等函数签名）【一方称】 | App 内置初始化，无用户侧插件入口 | 同左，按宿主协议接入 |
| 搜索能力 | **脚本内不做搜索**：search 由 App 内置平台 API 完成；自定义源只负责 `musicUrl` 取流（local 源额外支持 `lyric`/`pic`）【亲自精读】 | **插件自实现 search**（`ISearchFunc`：query + page → 结果列表）【一方称】 | listen1 内置各平台搜索 API | 音乐类视频源通常以"视频 → 音频流"方式被插件内搜索 |
| 取链（musicUrl） | `on(EVENT_NAMES.request, ...)` 回调返回 Promise，按 qualitys（128k/320k/flac/flac24bit）返回流 URL【亲自精读】 | 插件内直接实现 `musicUrl`，常依赖 headers 伪装 | 服务端聚合后对外统一 | 同 MusicFree 插件 |
| 沙箱 / 运行时 | App 内事件收发模型；`globalThis.lx.request` 不受跨域限制；提供 `utils.crypto`（aes/md5/rsa）与 `zlib`；移动版冻结 JS 内置原型防止污染【亲自精读】 | 早期 `vm.createContext` 隔离沙箱 + 10 秒执行超时，可用 axios/cheerio/crypto-js/dayjs 等内置模块【一方称】；新版迁移到 Extism WASI WASM，HTTP 必须用 PDK 客户端、只能读写 `/coverArt` 与 `/cache` 目录【一方称】 | 原生 / 服务端运行，无沙箱 | 同宿主协议 |
| headers / 反爬 | 由 `lx.request` 的 options 传入 method/headers/body/form/formData/timeout【亲自精读】 | 插件内自行构造 headers（Referer / User-Agent 伪装是常态）【一方称】 | 服务端处理 | 同左 |
| 代表源数量 | 社区活跃源约数十个（C1 清单内 8 个命名源）【一方称】 | 官方示例仓 + 第三方 hub 合计数十个插件【一方称】 | listen1 内置 6–7 个平台；any-listen 靠配置扩展 | B站源在 MusicFree / listen1 均有；YouTube 多见于海外客户端 |

**横评结论 ——「同一市场、多协议适配层」是必要的：**
1. **lx 与 MusicFree 的能力边界根本不同**：lx 脚本只做"取流"，搜索被锁在 App 内置 API 里；MusicFree 插件自实现搜索与取链。统一市场不能假设"装一个插件 = 全链路可用"，必须在适配层补全搜索（lx 模式）或裁剪搜索（仅取流模式）。
2. **沙箱强度差异决定安全模型**：lx 移动版用"冻结内置原型"做轻隔离；MusicFree 已演进到 WASI WASM 强隔离。统一市场应至少对齐 MusicFree 的强隔离方向，避免 lx 时代脚本可读写任意目录的问题。
3. **headers 与反爬是各源私有知识**：市场 manifest 应把 headers 模板下沉到适配层 / 源作者声明，而不是要求宿主 App 硬编码。

## 三、合规边界（关键事件与官方市场机制）

### 3.1 国内先例（亲自精读或有原文链接）

**事件 A：LX Music 2023-10-18 移除全部内置源【亲自精读，官方 FAQ】**
> "由于收到腾讯投诉，要求停止内置其平台的在线播放及下载服务，所以从 2023-10-18 起，LX Music 本身不再提供上述服务——移动版 v1.2.0 移除了所有内置自定义源，且旧版本内置的源也已失效。你需要编写或寻找别人分享的自定义源导入，才可正常使用。"
来源：`https://lxmusic.toside.cn/mobile/faq/cannot-play-and-download`
影响：官方从"内置源"退化为"纯空壳播放器 + 用户自导自定义源"，成为国内同类工具的标准避险范式。

**事件 B：MusicFree 官方示例插件仓库收到告知函【亲自精读，Gitee README】**
> "本仓库的插件只是示例，来自于网络公开的接口，并过滤掉所有 VIP/收费/试听歌曲。仅供学习参考使用……**收到了告知函，因此本示例插件仓库不再提供国内音乐厂商的源。**"
来源：`https://gitee.com/maotoumao/MusicFreePlugins`（附公众号文章 `https://mp.weixin.qq.com/s/NXww80a6YX4rbjwmepL48w`）
影响：连"示例仓"都被发函 → 只要仓库对外提供国内厂商取链能力，维护者个人即面临直接法律风险。

**事件 C（补充先例）：网易云第三方 API（NeteaseCloudMusicApi）2024-01 被要求删除【一方称：OSCHINA】**
> star 超 3 万的 Node.js 非官方网易云 API，因杭州网易云音乐有限公司法律通知要求下线盗链方法。
来源：`https://www.oschina.net/news/276411`

**事件 D（更早先例）：listen1 2017-11 被 QQ 音乐举报致代码库临时关闭【一方称】**
来源：`https://github.com/listen1/listen1_chrome_extension`（README 自述事件）

### 3.2 官方市场如何避免侵权 / 恶意内容（亲自精读）

**VS Code Marketplace（`https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security`）：**
- 每次发布 / 更新都用多引擎杀毒扫描，扫描未过不公开；
- 动态检测：在 clean room VM 沙箱中运行扩展验证运行时行为；
- Verified Publisher：域名所有权验证 + 连续 6 个月良好信誉才给蓝勾；
- 异常用量监控（下载 / 使用模式）；
- 防 name-squatting（抢注 Microsoft / RedHat / Copilot 等官方名）；
- Block List：恶意扩展下架后自动从用户端卸载；
- 扩展签名验证（发布即签名，安装时校验完整性与来源）；
- Secret Scanning（包内不得含 API key / 凭据）；
- 举报响应 SLA：1 个工作日内；
- 1.97 起第三方 Publisher 首次安装需用户信任确认。

**OctoPrint Plugin Repository（`https://plugins.octoprint.org/help/registering/`）：**
- 注册 = Fork 官方仓库 → 在 `_plugins/` 加一个 manifest MD → 提 PR → CI 校验站点与 feeds 合法 → 维护者合并后上架；
- 明确要求"主动维护"责任，完全 vibe-coded 的插件不收；
- 禁止安装时 / 加载时执行 setup.py 之外的隐藏代码；
- 与云服务交互的插件必须挂 Privacy Policy；
- 外部服务一律 https + 有效证书，禁止 http IP 直连；
- 外部服务不可达时必须优雅失败，不得拖垮宿主；
- 统计 / 埋点必须 opt-in；
- 强制属性声明：`cloud / commercial / free-tier / ai-developed`（commercial 插件后续剔除出公共统计，防刷量）。

### 3.3 对「星河音乐」默认市场地址策略的建议

**结论：采用「空默认 + 用户配置」，不内置任何第三方社区聚合地址；可选附一个自建 manifest 仅收录法律中立条目。**

理由（按优先级）：
1. **C3 已实证**：官方示例仓收到告知函即被强制剥离国内厂商源 → 任何内置指向"国内厂商取链"清单的默认地址，等于把项目主体暴露在与 LX Music / MusicFree 同等的投诉路径上。
2. **C1/C2/C7 不稳定**：高风险社区仓随时可能被删 / 换域名 / 被代理劫持，作为默认地址会直接造成用户端"源失效"体验；且它们无 License、内容来自互联网，不具备被官方背书的资格。
3. **VS Code / OctoPrint 范式的可迁移部分**：
   - 市场 manifest 必须有**签名 / 校验**（对齐 VS Code 扩展签名）；
   - 插件上架前过一次**静态扫描 + 沙箱跑通**（对齐 VS Code clean room VM / MusicFree WASI）；
   - 每条目强制声明 `source_type`（音源 / 插件 / 视频源）、`protocol`（lx / MusicFree / 自研）、`vendor_scope`（是否涉及国内厂商）、`privacy_policy_url`；
   - 提供**一键举报 + 下架后自动禁用**通道（对齐 VS Code block list）；
   - 对"国内厂商取链"类条目**默认不收录、不聚合、不推荐**，仅允许用户自行粘贴订阅 URL 时弹窗强提示合规风险（对齐 LX Music 现行模式）。
4. **自建 manifest 的中立白名单建议**（可安全内置）：
   - 本地文件 / 本地库（local 源）；
   - 用户自建 any-listen / Navidrome / Airsonic 类服务端（C9 范式）；
   - 明确无版权争议的互联网音频站（如自由音乐、翻唱平台、播客）；
   - 官方文档与脚本编写示例（对齐 C3 现状）。
5. **不推荐"社区中立源"作为默认**：当前生态中不存在已被验证、零国内厂商内容、且持续维护的中立市场（C4/C5/C6 均无审核），所谓中立源实际上只是风险被掩盖的社区 hub。
