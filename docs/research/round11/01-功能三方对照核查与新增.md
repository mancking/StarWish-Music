### a 类「代码有 / 用户无」（代码里定义了但用户完全用不到）

#### a14 新注册 IPC `cache:info`，渲染层零调用方，设置页无「播放缓存」卡片
- 证据：
  - `app/electron/ipc.ts:537` `'cache:info': () => playbackCacheInfo()`（diff 新增，注释「规格书 v2.8 · 1.12：播放缓存信息（音频 50 首 / 500MB，视频 1GB）」）；实现体在 `app/electron/core/cache.ts:127 cacheInfo()` 返回 `{audio:{files,bytes}, video:{files,bytes}, total}`。
  - 全仓 grep 渲染层 `call('cache:info')` = **0 命中**；`app/src/pages/Settings.vue` 缓存分组（:1744-1786）只有「封面缓存 / 媒体缓存 / 全部缓存」三张卡片，全部走旧 `cache:size`（:329/:623/:636）与 `cache:clear`（:739）。
- 影响：规格书 1.12 后端已把播放缓存（音频落盘 + 视频流上限 1GB）完整实现，但设置页没有任何入口展示「音频缓存 N 首 / 视频缓存 N」，用户看不到规格书承诺的缓存信息，后端 handler 是死通道。
- 解决方案：在 `Settings.vue` 网络与缓存分组（:1744 之后）新增「播放缓存」卡片，onMounted 与清理后 `cache.value` 并列调用 `call('cache:info')`，展示 `音频缓存 {{audio.files}} 首 · {{fmtBytes(audio.bytes)}} / 视频缓存 {{fmtBytes(video.bytes)}}`；并在「全部清理」按钮旁补一个只清播放缓存的按钮（接 c9 修正后的 `cache:clear`）。

#### a15 移动端原生播放缓存类 SwAudioCache 整类零引用（死代码）
- 证据：
  - `app/android/app/src/main/java/com/starwish/music/SwAudioCache.java:21-274` 完整实现了 hit/tee/info/clear/prune/open（50 首 / 500MB / LRU / Range）。
  - 全 `app/android/app/src/main` grep `SwAudioCache` 仅命中该文件自身（:21、:26）；`SwMediaClient.java:155 proxy()` 拦截 /swmedia/ 后直接 `HttpURLConnection` 拉流，**未调用 `SwAudioCache.hit()` 命中，也未用 `tee()` 边播边写**。
- 影响：规格书 1.12 移动端「在线歌曲播放后自动落盘、二次播放命中本地」完全不工作——原生类写好了但 WebView 请求拦截器没接线，移动端播放缓存是空转的。
- 解决方案：在 `SwMediaClient.proxy()`（:155）拉流前先 `File hit = SwAudioCache.hit(ctx, target)`，命中则用 `SwAudioCache.open(hit, range, meta)` 返回本地流（206）；远端响应为 200 且 mime 以 audio/ 开头时，把 `stream` 包成 `SwAudioCache.tee(ctx, target, stream)` 再喂给 WebResourceResponse；`cache:size`/`cache:clear` 桥接（见 b10）改调 `SwAudioCache.info/clear`。

#### a16 平台档位 `rotate` 字段在 CoverStage v2.8 重写后成为死字段
- 证据：
  - `app/src/platform/index.ts:26 rotate: boolean`、:99/:101/:103/:105 四档分别写 `rotate:false/false/true/true`。
  - 全仓 grep `.rotate` 消费点 = 0；`app/src/player-music/components/CoverStage.vue` 重写后 `spinning = computed(() => props.playing)`（diff 后 :31）直接判定，不再读 `platform.rotate`。
- 影响：规格 v2.8 · 1.2 已把四端统一为「圆形唱片、播放时旋转、暂停停转」，`tier.rotate` 仍按旧规则写「手机/车机不旋转」，与新规格矛盾且无人消费——后续维护者会误读它为有效开关。
- 解决方案：从 `PlatformTier`（platform/index.ts:17-31）删 `rotate` 字段及四档取值（:99/:101/:103/:105）；旋转规则只保留在 CoverStage。

### c 类「功能名 / key 不匹配」

#### c9 新增 `cache:clear`（1.12 播放缓存清理）被旧同名 handler 覆盖，新功能死在注册表里
- 证据：
  - `app/electron/ipc.ts:539` `'cache:clear': () => clearPlaybackCache()`（diff 新增，规格 1.12）。
  - `app/electron/ipc.ts:729` `'cache:clear': ({ scope = 'all' }: any = {}) => { … clearCoverCache() + readdirSync(mediaCacheDir()) + unlinkSync … }`（旧 handler，未动）。
  - 两者同在 `handlers: Record<string, Handler>` 对象字面量里，:729 在 :539 之后——JS 重复 key 后者胜出，运行时实际生效的是 :729。
  - 更糟：:729 用 `fs.readdirSync(mediaCacheDir())` 列根目录后 `fs.unlinkSync(path.join(dir, f))`——新增的播放缓存落在 `mediaCacheDir()/audio/`（cache.ts:22-24）与 `mediaCacheDir()/stream/`（media.ts streamDir）**子目录**，对目录 `unlinkSync` 抛错被静默吞掉，旧 handler 根本清不到这两个子目录里的文件。
- 影响：规格书 1.12「清除播放缓存」功能在桌面端完全失效——用户在设置页点清理，命中的是旧封面清理逻辑，且播放缓存（audio/stream 子目录）永远清不掉。这是本轮工作区改动直接引入的回归。
- 解决方案：把 :729 旧 handler 改名为 `'cache:clearCover'`（或并入新 handler 按 scope 分支）；让 :539 的 `cache:clear`（clearPlaybackCache，已递归清 audio/stream，见 cache.ts:134-150）成为唯一实现；同时核对 `Settings.vue:739` 的 `{ scope }` 调用改为新签名。

#### c10 设置项 `particle` 与渲染门控 `particle_phone` 双通道脱钩，设置开关对渲染无效
- 证据：
  - 设置侧：`app/src/settings/schema.ts:105 { key: 'particle', label: '粒子舞台' }`，`Settings.vue:1138` `@update:model-value="v => patch({ particle: v })"`，经 `ui.ts:157 patch → settings:set` 落到 electron 设置仓。
  - 渲染侧：`app/src/platform/index.ts:131` `if (tier.kind === 'phone') return lsGet('particle_phone') === '1'`，门控读 localStorage 键 `xinyuan_particle_phone`。
  - 全仓 grep `lsSet('particle_phone'` / `'particle_phone'` 写入 = **0 命中**（lsSet 仅用于 Player.vue:65 'lyrics_panel'、mobile/Player.vue:63 'brightness'）。
- 影响：用户在设置页切「粒子舞台」，渲染门控读的是另一条 localStorage 键、且从无人写——手机端粒子开关形同虚设；两条通道命名（`particle` vs `particle_phone`）也不一致。
- 解决方案：统一为单通道——`particlesAllowed()`（platform/index.ts:131）改为读 `ui.settings.particle`（与 schema key 对齐），删掉 `lsGet('particle_phone')` 分支；或反过来把设置 toggle 也写成 `lsSet('particle_phone', v?'1':'0')`，二选一。

#### c11 手机档粒子数被 `Math.max(particleCount(), 50)` 强制兜底成 50，绕过门控
- 证据：`app/src/pages/mobile/Player.vue:152` `:count="Math.max(particleCount(), 50)"`。手机档 `particleCount()`（platform/index.ts:135-139）因 c10 门控恒返回 0，`Math.max(0, 50)` 恒等于 50。
- 影响：与规格书 0.3「手机粒子默认关闭、低性能档 ≤80」矛盾——手机端只要切到粒子舞台就恒渲染 50 粒子，无论设置与性能档位。
- 解决方案：去掉 `Math.max` 兜底，改为 `:count="particleCount()"`（mobile/Player.vue:152），让 c10 修正后的真实门控与档位生效；舞台 `v-if="stage==='particle'"` 保留，但 count 由门控决定。

### d 类「描述过粗」（规格书只有简单描述、缺量化/验收标准）

#### d7 规格 1.12「播放缓存」只写容量上限，缺命中/清理/淘汰验收标准
- 证据：规格书 1.12 段仅「音频 50 首 / 500MB，视频 1GB，超出清最旧」；代码 `core/cache.ts` 已实现 LRU（:95-125）但规格未回填：二次命中后响应时间上限、Range 请求命中行为、清理后磁盘释放验证步骤、淘汰触发时机（每次写入后？切歌后？）。
- 影响：1.12 是本轮新落地功能，验收无标准，回归时无法判断「缓存命中是否真的比远端快」「清理是否真的释放磁盘」。
- 解决方案：规格 1.12 补验收：①同一首歌二次播放 media:// 请求耗时较首次下降 ≥50%（Range 206 命中 audio/ 文件）；②调 cache:clear 后 audio/ 目录文件数=0、磁盘释放量与 cacheInfo().total 一致；③LRU 在写入第 51 首时立即淘汰 mtime 最旧一首。

#### d8 竞品 P0⑥「续播断点圆点 + 缓冲灰层」无量化口径
- 证据：规格 6.0 竞品对齐 P0⑥ 仅描述「桌面视频进度条已缓冲灰色层 + 续播断点圆点」；代码侧 b3 已证实 player-video/ 完全无 buffered 渲染。规格未给：灰层宽度按 bufferedRanges 哪一段算、断点圆点直径/位置阈值、与拖动手柄的层级关系。
- 影响：b3 实现时无验收参照，灰层与圆点容易做成「有但对不上」。
- 解决方案：规格补：灰层 = buffered 最后一段 end / duration × 100%；断点圆点直径 8px、位置 = savedPosition/duration × 100%，仅当 savedPosition>15s 时显示；圆点与缓冲灰层都不拦截拖动事件。

#### d9 字幕延迟缺持久化 key 与跨视频记忆规则
- 证据：规格 2.11「字幕延迟 +0.5/-0.5/重置」未定义：偏移量存在哪个 key、是否跨视频记忆、与歌词偏移（schema:310 lyricOffset）是否同一条通道；代码 b11 两端 `@subtitle=undefined` 尚未实现。
- 影响：b11 补实现时无规格参照，容易做成「每次进视频重置」或与歌词偏移混为一谈。
- 解决方案：规格 2.11 补：字幕偏移存 `subtitleOffsetSec`（设置仓），跨视频记忆，范围 ±10s，步长 0.5s；与歌词偏移 `lyricOffset`（音乐侧）分开两条 key。
