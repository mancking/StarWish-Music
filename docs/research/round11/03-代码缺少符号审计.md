## S-01 ｜ cover.ts：`coverResolved` 在声明前被引用（TDZ 前向引用）

**证据**（`D:\music\app\electron\core\cover.ts`）：

```typescript
// 第 173-176 行：resolveCoverUrl 函数体内部引用了 coverResolved
export async function resolveCoverUrl(song: Song): Promise<string> {
  if (!song) return ''
  const cached = coverResolved.get(song.id)   // ← 这里用了 coverResolved
  if (cached) return cached
  if (resolving.has(song.id)) return resolving.get(song.id)!
  // ...
}

// 第 215 行：coverResolved 才声明（在函数定义之后 40 行）
const coverResolved = new Map<string, string>()
```

**影响**：
JavaScript 的 `const` 声明存在暂时性死区（TDZ）：模块顶层 `const coverResolved` 被提升到模块作用域顶部，但直到第 215 行执行前都处于"未初始化"状态。当前之所以没炸，是因为 `resolveCoverUrl()` 只在运行时被调用（模块加载完毕之后），第 215 行早已执行。但这是一个**脆弱的前向引用**：
- 如果未来有人在模块顶层加一行 `resolveCoverUrl(song)` 做预热/单测，会立即抛 `ReferenceError: Cannot access 'coverResolved' before initialization`。
- 如果有人把 `import` 顺序调整导致 `resolveCoverUrl` 被间接触发（例如某模块顶层 `await resolveCoverUrl(...)`），同样炸。
- ESLint 的 `no-use-before-define` 规则会标记此问题，但项目未开启该规则。

**解决方案**：
把第 215 行的 `const coverResolved = new Map<string, string>()` 上移到第 167 行附近（与 `resolving` 声明放在一起），改为：

```typescript
const resolving = new Map<string, Promise<string>>()
const coverResolved = new Map<string, string>()   // ← 上移到这里

export async function resolveCoverUrl(song: Song): Promise<string> {
  // ...
}
```

## S-02 ｜ download.ts:147：函数开括号与首语句挤在同一行（ASI/可读性隐患）

**证据**（`D:\music\app\electron\core\download.ts` 第 147 行）：

```typescript
async function streamTo(url: string, dest: string, signal: AbortSignal, onProgress: (r: number, got: number, total: number) => void): Promise<void> {  const headers: Record<string, string> = { 'User-Agent': UA, Accept: '*/*' }
```

**影响**：
函数体的开括号 `{` 之后**没有换行**，直接跟了 `const headers...`（两个空格间隔）。这在 JS 语法上合法，但带来两个隐患：
1. **可读性极差**：整行超过 200 列，函数签名和第一行逻辑糊在一起，Code Review / 调试时几乎无法一眼看出函数边界。
2. **ASI 陷阱**：如果未来有人在 `const headers` 之前插入一条以 `(` 或 `[` 开头的语句（例如 `const retry = (...args) => ...`），由于上一行（函数签名行）以 `{` 结尾而非分号，ASI 不会插入分号，引擎会把它解析为"对 `{` 后的对象字面量做函数调用"——直接报 `SyntaxError` 或行为异常。当前项目其他所有函数都遵守 `{\n  const ...` 的换行规范，唯独这一行漏了。

**解决方案**：
在 `{` 后加换行：

```typescript
async function streamTo(url: string, dest: string, signal: AbortSignal, onProgress: (r: number, got: number, total: number) => void): Promise<void> {
  const headers: Record<string, string> = { 'User-Agent': UA, Accept: '*/*' }
```

## S-03 ｜ music-service.ts:155：`const kw = ''` 死变量（重构残留）

**证据**（`D:\music\app\electron\core\music-service.ts` 第 152-165 行）：

```typescript
function mergeSongs(list: Song[], limit: number): Song[] {
  const out: Song[] = []
  const seen = new Set<string>()
  const kw = ''                          // ← 声明了但从未使用
  for (const s of list) {
    if (!s || !s.name) continue
    const key = dedupeKey(s)
    if (!key || seen.has(key)) continue
    seen.add(key)
    out.push(s)
    if (out.length >= limit) break
  }
  return out
}
```

**影响**：
`kw` 是一个空字符串常量，声明后在整个函数体内从未被读取。从代码演进看，这是早期版本 `mergeSongs(list, limit, keyword)` 接受关键词参数做相关性排序的残留——后来排序逻辑移到了 `rankByQuery()`，`kw` 参数被删除但这行声明忘了清。当前不影响运行，但：
- 读代码的人会误以为 `kw` 在某处被用到（可能在条件判断里），浪费排查时间。
- 如果有人后续想加回关键词过滤，可能会误用这个空串而不是传入实际参数，导致过滤逻辑静默失效。

**解决方案**：
删除第 155 行 `const kw = ''`。

## S-04 ｜ lrc.ts:79-80：`trans: undefined` 展开与后续直接赋值不一致（语义脆弱）

**证据**（`D:\music\app\shared\lrc.ts` 第 78-81 行）：

```typescript
for (const t of times) {
  entries.push({ time: t, text, ...(words ? { trans: undefined } : {}) })
  if (words) (entries[entries.length - 1] as any).words = words
}
```

**影响**：
当 `words` 存在时，逻辑分两步：
1. push 一个对象，通过展开 `{ trans: undefined }` **显式注入** `trans` 键（值为 `undefined`）。
2. 再通过 `(entries[...].words = words)` **直接挂载** `words` 属性。

这种"先展开注入 undefined 键、再直接赋另一个键"的写法很绕。注释（第 86 行）说这样做是为了让后续翻译配对逻辑能区分"有逐字歌词的行"和"翻译行"。但实际配对逻辑（第 90 行）用的判断是：
```typescript
const isTrans = last && Math.abs(last.time - e.time) < 0.05 && last.text !== e.text && !(e as any).words
```
它判断的是 `!(e as any).words`，**并不依赖 `trans` 键是否存在**。也就是说，`{ trans: undefined }` 这个展开是多余的——它既不是配对判断的依据，也不影响任何行为。真正起作用的是第 80 行的 `words` 赋值。

隐患：如果未来有人重构配对逻辑、改成检查 `e.trans === undefined` 来判断"这是不是原文行"，会发现原文行的 `trans` 恰好是 `undefined`（因为我们手动注入了），翻译行的 `trans` 是另一条歌词的 text——逻辑看似对，但这个隐式约定完全靠注释维持，非常脆弱。

**解决方案**：
把两步合并为一次 push，去掉多余的 `trans: undefined` 展开：

```typescript
for (const t of times) {
  if (words) entries.push({ time: t, text, words })
  else entries.push({ time: t, text })
}
```

## S-05 ｜ mobile/player.ts:243-248：嵌套三元表达式混入布尔短路（可读性/误读风险）

**证据**（`D:\music\app\src\mobile\player.ts` 第 243-249 行）：

```typescript
const pic = song?.pic || ''
const url = /^https:\/\//i.test(pic)
    ? pic
    : /^http:\/\//i.test(pic) && !isNativeWebView()
      ? pic
      : ''
return url ? [{ src: url, sizes: '512x512', type: 'image/jpeg' }] : []
```

**影响**：
这是一个三层嵌套三元，中间层混入了 `&& !isNativeWebView()` 短路条件。逻辑拆解：
- `pic` 是 `https://` → 用 `pic`
- `pic` 是 `http://` **且** 不是原生 WebView → 用 `pic`
- 其他情况 → 空串

中间层的 `&& !isNativeWebView()` 是关键安全条件（原生 WebView 不允许 http:// 混合内容加载封面），但它藏在嵌套三元的第二个条件里，缩进对齐又和外层三元的"冒号分支"视觉上混淆。Code Review 时极易误读为"只要是 http:// 就用 pic"，漏掉原生 WebView 下必须置空的约束。如果未来有人简化这个三元（例如改成 `const url = /^https?:\/\//.test(pic) ? pic : ''`），会悄悄在 Android 真机上导致封面图全部加载失败（混合内容策略拦截）。

**解决方案**：
把条件拆成命名布尔值，消除嵌套三元：

```typescript
const pic = song?.pic || ''
const isHttps = /^https:\/\//i.test(pic)
const isHttp = /^http:\/\//i.test(pic)
const allowHttpCover = isHttp && !isNativeWebView()
const url = isHttps || allowHttpCover ? pic : ''
```
