## 一、Bug 97+（逻辑错误 / BUG / 遗漏）

### Bug97｜`player:rate` IPC handler 不持久化 playbackRate，桌面端倍速重启后丢失

- 证据：
  - `electron/ipc.ts:417-420`：
    ```
    'player:rate': ({ rate }: any) => {
      player.setRate(Number(rate) || 1)
      return decState(player.getState())
    },
    ```
    对比同文件相邻 handler：
    - `player:volume`（:403-407）末尾 `saveSettings({ volume: Number(volume) })`
    - `player:mode`（:412-416）末尾 `saveSettings({ playMode: mode })`
    - `player:quality`（:427-431）末尾 `saveSettings({ quality })`
    `player:rate` 唯独漏了 `saveSettings({ playbackRate: rate })`。
  - `src/stores/player.ts:311-317` `setRate()` 直接 `call('player:rate', ...)`，不走 `ui.patch({playbackRate})`。
  - 主进程 `player-service.ts:461-466` `setRate()` 只 `send({type:'rate'})` + `emitState()`，不落盘。
- 影响：用户通过播放控制条 cycleRate/setRate 切到 1.25×/1.5× 后，重启 App 倍速回到 1.0；与规格书 1.15「倍速持久化」不符。与 Bug91（移动端同类）对称，桌面端此前漏列。
- 解决方案：`electron/ipc.ts:417-420` handler 末尾追加 `saveSettings({ playbackRate: Number(rate) || 1 })`；与 `settings:set` 分支（:240 `if (typeof patch.playbackRate === 'number') player.setRate(...)`）保持双向一致。
- 适用端：桌面。

### Bug98｜`broadcast()` 只向 main+lyric 两窗广播，taskbar 窗永远收不到 player:state/tick，任务栏歌词静态不动

- 证据：
  - `electron/windows.ts:405-416`：
    ```
    export function broadcast(channel: string, payload: any): void {
      for (const key of ['main', 'lyric'] as const) {
        const w = wins[key]
        if (w && !w.isDestroyed()) { try { w.webContents.send(channel, payload) } catch {} }
      }
    }
    ```
    数组里**没有 `'taskbar'`**。
  - `electron/main.ts:343` `player.setBroadcast(broadcast)`，:375-384 仅包一层加 tray 菜单刷新，未扩展目标窗。
  - `src/pages/TaskbarLyric.vue:14-22` 用 `usePlayerStore()`，`player.displayPosition` / `player.lyric` 全靠 `on('player:state'|'player:tick')` 驱动（stores/player.ts:122-128）。
  - 全仓 grep `wins.taskbar.webContents.send` 仅 0 命中；`sendToMain` 只发主窗。
- 影响：用户开启「任务栏歌词」后，浮条只在 init 时通过 `call('player:state')` 拿到一次性快照，之后切歌/暂停/进度推进全部不更新——歌词高亮停在第一句，播放中圆点也不亮，功能形同虚设。
- 解决方案：`windows.ts:406` 把 `['main','lyric']` 扩为 `['main','lyric','taskbar']`；taskbar 窗 `focusable:false`/`setIgnoreMouseEvents(true)` 不影响收消息。同时检查 `player:spectrum` 等高频事件是否需要发 taskbar（建议不发，taskbar 不用频谱）。
- 适用端：桌面。

### Bug99｜`restoreSession()` 只恢复 UI 状态、从未给 host 发 `load`，重启后点播放「无声」

- 证据：
  - `electron/core/player-service.ts:162-174`：
    ```
    restoreSession(): void {
      const last = dbGetSetting<{ songId; position }>('player.last')
      if (!last?.songId) return
      const song = getSong(last.songId)
      if (!song) return
      this.state.song = song
      this.state.queue = [song]
      this.state.index = 0
      this.state.position = Math.max(0, Number(last.position) || 0)
      this.state.duration = song.duration || 0
      this.state.status = 'paused'
      this.emitState()
    }
    ```
    全程没有 `this.send({type:'load',...})`，host 的 `<audio>` 元素 `src` 仍为空。
  - `electron/main.ts:346` `if (getSettings().rememberPosition) player.restoreSession()` 在 `player.attachHost(audio)`（:344）之后调用，但 attachHost 的 `did-finish-load` 分支（player-service.ts:63-71）只补 `pendingLoad`，restoreSession 没设置 pendingLoad。
  - 用户点播放 → `player.toggle()`（player-service.ts:395-415）：status='paused' 落到 :411 `this.send({type:'play'})`，并把 status 置 'playing' 广播出去。
  - host 收到 `play` 命令（player-host.ts:301-315）：`audio.play()` 在无 src 上 reject，`AbortError` 被 :311 静默吞掉，不发 error。
- 影响：开启「记忆播放位置」后，重启 App 看到歌曲标题/进度条都在，点播放按钮 UI 变成「playing」但实际无声音、进度条不走；用户必须手动切一首歌才能恢复播放。
- 解决方案：`restoreSession()` 末尾追加 `this.pendingLoad = { type:'load', url:`swmedia://stream/?u=${encodeURIComponent('')}`, autoplay:false, startAt: this.state.position, ... }` 不合适——更直接的做法：restoreSession 后调用 `this.load(song, false, this.state.position)`（load 内部会 resolveUrl 并发 host），让 host 真正挂上 src；或在 toggle() 的 paused 分支判断 `if (!hostHasSrc) this.load(this.state.song, true, this.state.position)`。
- 适用端：桌面。

### Bug100｜`player-host.ts` `fadeTo()` 用 `requestAnimationFrame`，隐藏窗口里 `audio.pause()` 回调可能不执行，按暂停不暂停

- 证据：
  - `electron/player-host.ts:162-178` `fadeTo()`：rAF 循环驱动音量线性过渡，`done` 回调在 rAF 链最后一帧调用。
  - `electron/player-host.ts:316-322` pause 命令：
    ```
    case 'pause':
      fadeTo(0, Math.min(200, fadeMs), () => {
        audio.pause()
        audio.volume = muted ? 0 : targetVolume
        state('paused')
      })
    ```
    `audio.pause()` 依赖 fadeTo 的 done 回调。
  - `electron/windows.ts:197-211` audio host 是 `show:false, skipTaskbar:true, frame:false` 的隐藏窗。Chromium 对不可见窗口的 rAF 在部分平台/机型上会被节流到 0（尤其 `backgroundThrottling:false` 只解 IO 不解合成帧）。
  - 对照：`player-host.ts:265-267` load 前 fade-out 也用 rAF；:284 autoplay 后 fade-in 也用 rAF。
- 影响（待核实）：在某些 Windows 环境/电源策略下，用户点暂停后 fadeTo 的 rAF 不触发，`audio.pause()` 永远不被调用——歌曲继续播，UI 却已显示 paused。同样 crossfade 切歌时旧歌 fade-out 卡住。
- 解决方案：把 `fadeTo` 的驱动从 rAF 改成 `setTimeout` 逐帧推进（hidden window 里 setTimeout 仍正常），或在 fadeMs<=0 时直接同步 done；保留 rAF 仅作为「可见窗时更平滑」的快路径。
- 适用端：桌面。

### Bug101｜移动端 `runDownload` 把整曲 chunks 全堆内存，30MB FLAC 峰值 60MB+，手机端易 OOM

- 证据：
  - `src/mobile/bridge/index.ts:806-822`：
    ```
    const chunks: Uint8Array[] = []
    for (;;) {
      const { done, value } = await reader.read()
      if (done) break
      chunks.push(value)
      ...
    }
    ```
  - :824-829 `const all = new Uint8Array(received); for (const c of chunks) { all.set(c, off); off += c.length }`——又复制一份。
  - :833-837 调 `bytesToBase64(all)`（:727-734）再编码一份 base64 字符串。
  - 峰值内存 ≈ chunks 数组（≈received）+ all（received）+ base64（received×1.33）≈ 3.3× 文件大小。30MB FLAC → ~100MB 峰值。
- 影响：移动端 WebView 内存配额远低于桌面，连续下载多首无损时 OOM 杀进程；与桌面 Bug96 同类但移动端更严重。
- 解决方案：原生 `SwBridge.saveToMedia` 若支持流式写入，应逐 chunk `nativeCall('SwBridge','writeChunk',{data:btoa(value)})`；若不支持流式，至少把 chunks 写 IndexedDB 临时 Blob 再合并，避免同时驻留三份。
- 适用端：移动。

### Bug102｜移动端 `saveVideoOffline` 整片 `arrayBuffer()` 读入内存，300MB 视频峰值 400MB+

- 证据：
  - `src/mobile/bridge/index.ts:765-787`：
    ```
    const res = await fetch(src)
    if (!res.ok) throw ...
    const total = Number(res.headers.get('content-length') || 0)
    if (total > 300 * 1024 * 1024) throw new Error('视频超过 300MB，暂不支持离线缓存')
    const all = new Uint8Array(await res.arrayBuffer())
    const ret = await nativeCall('SwBridge', 'saveToMedia', {
      name: ..., mime: 'video/mp4', data: bytesToBase64(all),
    })
    ```
  - 300MB × (1 + base64 0.33) ≈ 400MB+ 内存驻留。手机 WebView 单 tab 通常 256-512MB 上限。
- 影响：用户离线缓存一个 200MB 的 MV，WebView 直接被系统回收；进度条也不可见（全程 await arrayBuffer）。
- 解决方案：要求原生 `SwBridge.saveToMedia` 支持流式（传入 `/swmedia/?u=...` 让原生自己下载）；或把 300MB 上限砍到 80MB，并在下载期间通过 `download:progress` 广播进度。
- 适用端：移动。

### Bug103｜`scanLibrary` 只增不删，用户从磁盘删除文件后 DB 残留死链

- 证据：
  - `electron/core/library.ts:89-195` `scanLibrary` 全程只 `saveSongs(batch)`（UPSERT），没有任何 `DELETE FROM songs WHERE local_path NOT IN (...)` 或基于 mtime/存在性的清理。
  - `electron/core/db.ts:450-459` `removeLocalSongs(paths)` 仅在 `library:remove` IPC（ipc.ts:575-579）手动调用时触发。
  - 对比：用户在文件管理器直接删歌，App 不知道；下次扫描 `walk` 不再列出该文件，但 DB 行还在，`localSongs()` 仍返回它。
- 影响：本地音乐列表越用越长死链；点死链 → resolveUrl 拿不到 localPath → 报错；收藏/歌单里引用的歌曲也变成空壳。
- 解决方案：scanLibrary 末尾收集本次 `files` 列表对应的 localPath，与 DB 中 `source='local'` 的所有 localPath 做差集，差集中「磁盘上已不存在」的走 `removeLocalSongs(deadPaths)`；同时清理 playlist_song/favorites 引用。
- 适用端：桌面。

### Bug104｜移动端 `setQuality` 切音质不保留播放位置，歌曲从头重播

### Bug105｜定时关闭 `setSleepTimer` 不持久化 `sleepTimerMin`，重启后定时丢失

- 证据：

### Bug106｜桌面 `setQuality` 不重置 `failures`/`consecutiveFails`，切音质后下次失败直接跳歌

- 证据：
  - `electron/core/player-service.ts:509-517`：
    ```
    setQuality(q: string): void {
      if (this.state.quality === q) return
      this.state.quality = q
      this.emitState()
      if (this.state.song && this.state.status !== 'idle') {
        const pos = this.state.position
        this.load(this.state.song, this.state.status === 'playing', pos)
      }
    }
    ```
    没有 `this.failures = 0; this.consecutiveFails = 0; this.lastResolved = null`。
  - 对照 `playAt`（:247-259）切歌时显式 `this.failures = 0`。
  - `handlePlaybackError`（:299-331）依赖 `this.failures <= 2` 判断是否换源重试。
- 影响：用户在 flac 失败一次后切到 320k 音质重试，failures 仍=1；新流一旦再失败一次，failures=2 仍会触发换源，但 consecutiveFails 若此前已累加到 2，下次失败直接 toast「连续多首失败」而不是正常换源。边界态，弱网下偶发。
- 解决方案：`setQuality` 在调 load 前追加 `this.failures = 0; this.consecutiveFails = 0; this.lastResolved = null`。
- 适用端：桌面。

### Bug107｜`saveSession` 只存 songId+position，重启后队列/播放模式/音量全丢

- 证据：
  - `electron/core/player-service.ts:176-179`：

  - `src/player-video/components/VideoStage.vue:74` 注释 `// AB 段循环（规格书 2.2）：到达 B 点回到 A 点`——只是注释，无实际 A/B 点设置 UI，无 `loopA/loopB` 状态变量。

- 解决方案：PlaySettingsSheet 加「AB 循环」开关：开启后进度条下方两个小按钮「设为 A / 设为 B」，timeupdate 监听若 `currentTime >= loopB && loopB > loopA` 则 `currentTime = loopA`。
- 适用端：桌面 + 移动。

### F-16｜车机模式下 MV 进入未强制「音频模式」，与规格书 2.1 不符

- 证据：
  - 规格书 2.1（HTML:603）：「车机进入视频默认直接是音频模式（驾驶不看画面，见 2.12）」。

  - CarPlayer.vue 只是音乐播放页，没有 MV 入口；但用户可通过歌单里的 MV 歌曲跳转 `/mv/:bvid`，车机 WebView 同样会走到这两个页面。
- 影响：驾驶中切到 MV 直接全屏视频画面，违反驾驶勿扰原则。
- 解决方案：MvPlayer.vue onMounted 判断 `if (platform.value.car) session.setAudioMode(true)`，VideoStage 在 car 时强制替换为 AudioModeView（封面+歌词+控件）。
- 适用端：车机。
