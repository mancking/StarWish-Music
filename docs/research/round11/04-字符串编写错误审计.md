# 04 · 字符串编写错误审计（round11）

> 范围：`D:\music\app\src/`、`electron/`、`shared/`、`scripts/`、`web/` 下 `.ts/.js/.vue/.mjs/.cjs/.html`。
> 方法：提取渲染层 `call('<channel>')` 全集与主进程 `handlers` 注册表 key 做差集；提取 `broadcast/sendToMain` 事件与渲染层 `on(...)` 白名单做差集；grep localStorage key / dbSetSetting key / 硬编码 UI 文案。

## T-01 【Critical · 数据丢失】`video:offline:remove` 载荷字段名错误 → 误删全部离线视频

**证据**
- 渲染层发送：`D:\music\app\src\pages\MvPlayer.vue:173`
  ```ts
  await call('video:offline:remove', { bvid: bvid.value, cid: p.cid })
  ```
- 主进程注册：`D:\music\app\electron\ipc.ts:550`
  ```ts
  'video:offline:remove': ({ key }: { key?: string }) => removeOfflineVideos(key),
  ```
- 主进程实现：`D:\music\app\electron\core\media.ts:229`
  ```ts
  export function removeOfflineVideos(key?: string): boolean {
    const keys = key ? [key] : Object.keys(map)   // key 为空 → 清空全部
  ```
- 对比正确用法：`D:\music\app\src\pages\OfflineCache.vue:68`
  ```ts
  await call('video:offline:remove', { key })
  ```

**影响**
MvPlayer 页点"删除离线缓存"时，主进程从 `payload` 里取 `key`，但渲染层给的是 `{bvid, cid}`，`key === undefined`。按 `media.ts:231` 的 fallback 分支，这会把**整个离线视频清单里的所有条目全部删掉**（不止当前这一集）。用户以为只删当前 MV，结果所有已缓存的离线视频文件被一次性清空。

**解决方案**
二选一，推荐方案 A（改动最小、与 OfflineCache 面板一致）：
- **方案 A（改渲染层）**：`MvPlayer.vue:173` 改为先算出 key 再传。但 `offlineKey` 是主进程内 `crypto.sha1(`${bvid}:${cid}`)`，渲染层算不了。因此更稳的是方案 B。
- **方案 B（改主进程）**：在 `ipc.ts:550` 增加 bvid/cid 兜底派生 key：
  ```ts
  'video:offline:remove': ({ key, bvid, cid }: { key?: string; bvid?: string; cid?: string }) => {
    const k = key || (bvid && cid ? offlineKey(bvid, cid) : undefined)
    return removeOfflineVideos(k)
  },
  ```
  同时把 `offlineKey` 从 `media.ts` export 出来。这样 `{bvid, cid}` 也能正确只删当前条目，OfflineCache 面板传 `{key}` 的老路径不受影响。

## T-02 【High · 功能失效】`video:offline:save` 缺必填 `url` 字段 → 桌面端"缓存到本地"永远失败

**证据**
- 渲染层发送：`D:\music\app\src\pages\MvPlayer.vue:177`
  ```ts
  await call('video:offline:save', { bvid: bvid.value, cid: p.cid, qn: session.qn.value, title: session.title.value })
  ```
- 主进程注册：`D:\music\app\electron\ipc.ts:543`
  ```ts
  'video:offline:save': async ({ bvid, cid, url, title }: { bvid: string; cid: string; url: string; title?: string }) => {
    if (!url) throw new Error('缺少视频地址')
    return saveOfflineVideo(bvid, cid, url, title)
  },
  ```
- 移动端桥接同样要求 `url`：`D:\music\app\src\mobile\bridge\index.ts:585`
  ```ts
  'video:offline:save': async ({ url, title }: any) => await saveVideoOffline(String(url || ''), ...),
  ```

**影响**
MvPlayer 点"下载/缓存"按钮时，渲染层传的是 `qn`（清晰度）而不是当前正在播放的流地址 `url`。主进程 `if (!url) throw new Error('缺少视频地址')` 必然命中，toast 永远是"缺少视频地址"。该按钮在桌面端与移动端都是死按钮，规格书 3.5 的 MV 离线缓存能力实际不可用。

**解决方案**
`MvPlayer.vue:177` 改为传当前流地址（同文件 353 行已经取过 `session.src.value`）：
```ts
await call('video:offline:save', {
  bvid: bvid.value,
  cid: p.cid,
  url: session.src.value,          // ← 必填，原来漏了
  title: session.title.value,
})
```
注意：`session.src.value` 必须是已解析出的 mp4/flv 直链（`music:mvurl` 返回的 `r.url`），而不是 blob 或 m3u8；如果当前是 MSE/Blob 播放，需要先重新调一次 `music:mvurl` 拿到可下载的 http url 再传。

## T-03 【High · 功能失效】`cache:clear` 在 handlers 对象里重复注册，后者覆盖前者，规格书 1.12 播放缓存永远清不掉

**证据**
- 第一次注册（期望清播放缓存 audio/stream 子目录）：`D:\music\app\electron\ipc.ts:539`
  ```ts
  /* 规格书 v2.8 · 1.12：清除播放缓存（不删除已下载文件） */
  'cache:clear': () => clearPlaybackCache(),
  ```
- 第二次注册（清封面 + mediaCacheDir 顶层文件）：`D:\music\app\electron\ipc.ts:729`
  ```ts
  // scope: cover | media | all
  'cache:clear': ({ scope = 'all' }: any = {}) => {
    if (scope === 'all' || scope === 'cover') clearCoverCache()
    if (scope === 'all' || scope === 'media') {
      const dir = mediaCacheDir()
      for (const f of fs.readdirSync(dir)) fs.unlinkSync(path.join(dir, f))
    }
    ...
  },
  ```
- 真正实现播放缓存清理的函数：`D:\music\app\electron\core\cache.ts:134` `clearPlaybackCache()`，它遍历 `audioCacheDir()`（`mediaCacheDir/audio`）和 `videoCacheDir()`（`mediaCacheDir/stream`）两个子目录。
- 渲染层按规格书调用：`D:\music\app\src\storage\cache.ts:27` `clearCache()` → `call('cache:clear')`。

**影响**
JS 对象字面量同名 key 后者覆盖前者，所以 539 行的 `clearPlaybackCache()` 永远不会被执行。更糟的是，729 行的 `media` 分支只 `readdirSync(mediaCacheDir())` 顶层文件并 `unlinkSync`，**不会递归进 `audio/` 和 `stream/` 子目录**（对目录 `unlinkSync` 会抛错被 catch 吞掉）。结果：
1. 规格书 1.12 要求的"清除播放缓存（音频 50 首 / 500MB、视频 1GB）"实际清不掉任何东西；
2. `src/storage/cache.ts:clearCache()` 拿到的返回是 `{cover, media, total}`，但它的 `CacheInfo` 接口是 `{audio, video, total}`，`r.audio / r.video` 都是 undefined，UI 显示为 0；
3. `cache:size`（ipc.ts:616）同样只统计 `mediaCacheDir()` 顶层文件，子目录里几百 MB 的播放缓存一直被漏报。

**解决方案**
- 删除 `ipc.ts:539` 的重复 key（或把 729 行重命名为 `cache:purge`，让 539 行保留为 `cache:clear` 的真正实现）。
- 让 729 行的 media 分支改为递归删除 `audio/`、`stream/` 子目录内容（直接复用 `clearPlaybackCache()`），并让返回值统一为 `{cover, audio, video, total}` 形状，与 `src/storage/cache.ts` 的 `CacheInfo` 对齐。
- `ipc.ts:616` 的 `cache:size` 同样改为递归统计 `audio/` 和 `stream/`。

## T-04 【Medium · 功能失效】`src/storage/db.ts` 调用了不存在的 IPC 通道 `history:list` / `history:add`

**证据**
- 渲染层：`D:\music\app\src\storage\db.ts:20-21`
  ```ts
  history: (limit = 120) => call<Song[]>('history:list', { limit }).catch(() => [] as Song[]),
  addHistory: (song: Song, ms = 0) => call('history:add', { song, ms }).catch(() => null)
  ```
- 主进程注册（桌面）：`D:\music\app\electron\ipc.ts:471-472`
  ```ts
  'db:history': ({ limit }: any) => decList(historySongs(limit || 100)),
  'db:history:add': ({ song, ms }: any) => { addHistory(song, ms || 0); return true },
  ```
- 移动端桥接同样注册：`D:\music\app\src\mobile\bridge\index.ts:477-478`
  ```ts
  'db:history': ({ limit }: any) => historySongs(limit || 100),
  'db:history:add': ({ song, ms }: any) => { addHistory(song, ms || 0); return true },
  ```
- 正确调用样例：`D:\music\app\src\stores\library.ts:35,153,177` 都用 `db:history` / `db:history:clear`。

**影响**
`call('history:list')` 会命中 `ipc.ts:862` 的 `未实现的能力：history:list` 分支，返回 `{ok:false, error}`。当前 `src/storage/db.ts` 没有被任何文件 import（grep `storage/db` 全仓 0 命中），属于死代码，但一旦有人按模块注释"渲染层只通过这里访问曲库"去用 `db.history()` / `db.addHistory()`，会静默失败（被 `.catch(() => [])` 吞成空数组）。

**解决方案**
`src/storage/db.ts:20-21`：
```ts
history: (limit = 120) => call<Song[]>('db:history', { limit }).catch(() => [] as Song[]),
addHistory: (song: Song, ms = 0) => call('db:history:add', { song, ms }).catch(() => null)
```

## T-05 【Medium · 规范违反】Sidebar 折叠状态绕过 `lsGet/lsSet`，使用 `sw.` 前缀裸 localStorage key

**证据**
- `D:\music\app\src\components\Sidebar.vue:20,23`
  ```ts
  const collapsed = ref(localStorage.getItem('sw.sidebar.collapsed') === '1')
  ...
  localStorage.setItem('sw.sidebar.collapsed', collapsed.value ? '1' : '0')
  ```
- 统一前缀工具：`D:\music\app\src\platform\index.ts:33-46`
  ```ts
  const PREFIX = 'xinyuan_'
  export function lsGet(name: string): string | null { return localStorage.getItem(PREFIX + name) }
  export function lsSet(name: string, value: ...): void { localStorage.setItem(PREFIX + name, String(value)) }
  ```
- 规格书 0.5 要求：所有持久化 key 统一 `xinyuan_` 前缀（注释见 `src/main.ts:23`、`src/stores/download.ts:42`）。
- 其它所有 key 都走 `lsGet/lsSet`：`car` / `low_perf` / `platform` / `lyrics_panel` / `eq_preset` / `visual_mode` / `loop_mode` / `particle_phone` / `brightness`。

**影响**
1. 命名空间违反：唯一一个 `sw.` 前缀的 localStorage key，迁移工具 / 清空工具按 `xinyuan_` 前缀枚举时会漏掉它，导致用户点"清除本地数据"后侧边栏折叠状态残留；
2. 不统一：其它模块全部走 `lsGet/lsSet` 自动加前缀，Sidebar 直接裸写，后续维护者很难一眼看出这是同一套存储。

**解决方案**
`Sidebar.vue:20,23` 改为：
```ts
import { lsGet, lsSet } from '@/platform'
const collapsed = ref(lsGet('sidebar_collapsed') === '1')
function toggleCollapse(): void {
  collapsed.value = !collapsed.value
  lsSet('sidebar_collapsed', collapsed.value ? '1' : '0')
}
```
（老 key `sw.sidebar.collapsed` 建议在 `main.ts` 启动时一次性迁移：读到老值就 `lsSet('sidebar_collapsed', old)` 并 `removeItem('sw.sidebar.collapsed')`。）

> 备注：`src/stores/player.ts:30,396` 里的 `sw.stage` 是**有意保留**的旧 key 迁移读路径（读到后立即 `removeItem` 并写入新 key `xinyuan_visual_mode`），属于正确做法，不在此列。

## T-06 【Low · 形状不一致】`cache:info` 与 `cache:clear` 返回结构不对称，`src/storage/cache.ts` 的 `CacheInfo` 与实际返回对不上

**证据**
- 渲染层接口定义：`D:\music\app\src\storage\cache.ts:8-18`
  ```ts
  export interface CacheInfo {
    audio: { files: number; bytes: number }
    video: { files: number; bytes: number }
    total: number
  }
  ```
- `cache:info` 实际返回：`D:\music\app\electron\ipc.ts:537` → `playbackCacheInfo()` → `D:\music\app\electron\core\cache.ts:127` `cacheInfo()` 返回 `{audio, video, total}` ✅ 匹配。
- `cache:clear` 实际返回（覆盖后生效的 729 行）：`{cover, media, total}` ❌ 没有 `audio` / `video` 字段。
- 移动端桥接：`D:\music\app\src\mobile\bridge\index.ts:618` `'cache:clear': () => ({ cover: 0, media: 0, total: 0 })`。

**影响**
`src/storage/cache.ts:clearCache()` 返回的 `r` 上 `r.audio` / `r.video` 都是 `undefined`，但函数只判 `typeof r.total === 'number'` 就把 `r` 原样返回。任何下游如果按 `CacheInfo` 去读 `r.audio.bytes` 会直接抛 `Cannot read properties of undefined`。当前没有下游用这个模块（死代码），但接口形状与实现不一致是个埋着的雷。

**解决方案**
与 T-03 一起修：把 `cache:clear` 的返回值统一成 `{cover, audio, video, total}`，并在 `src/storage/cache.ts` 的 `CacheInfo` 里补 `cover` 字段（或明确分两个接口 `PlaybackCacheInfo` 和 `CoverCacheInfo`，不要混用）。
