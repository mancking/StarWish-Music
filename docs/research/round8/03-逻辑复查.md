# 第八轮调研 · 03 逻辑错误/遗漏全面复查

> 范围：`D:\music\app\src`、`electron/`、`preload.js`、`shared/`（跳过 node_modules / dist / .tmp / _legacy）。
> 方法：只读代码、按六个维度（状态机边界 / 空值 / 事件竞态 / 异步时序 / 内存泄漏 / 数据一致性）逐项取证，仅报有行号证据的问题。

## Bug 46 | mobile/player.ts 中 HTMLMediaElement `error` 事件与 `el.play()` catch 双重处理失败，retryCount 被双倍递增，一次网络错误即耗尽重试

- 现象：`src/mobile/player.ts:130-148`（`load()` 的 catch 块）与 `src/mobile/player.ts:210-220`（`el.addEventListener('error', ...)`）对同一次媒体加载失败都会执行 `markSourceFailed()` + `retryCount++` + `load(i, true, true)`。
  - 125 行 `el.src = ...`、127 行 `if (autoplay) await el.play()`：网络失败时浏览器既触发 `error` 事件（任务队列异步），又使 `play()` 的 Promise reject 进入 130 行 catch。
  - 时序上：`error` 处理器先把 `retryCount` 从 0 加到 1 并 `void load(index, true, true)`；随后 `play()` reject 进入 catch，`index === i` 成立（新 load 尚未返回），再次 `markSourceFailed()`、`retryCount++` 到 2，`retryCount < MAX_RETRY(2)` 不成立，直接 `failCurrent()`。
- 影响：弱网/单条死链时，本应「换源重试 2 次」的逻辑被压缩成「一次失败即跳歌」，`consecutiveFails` 快速累积，用户感知为「连播好几首都失败」。
- 解决方案：在 `el.addEventListener('error', ...)` 内与 `load()` 的 catch 之间加互斥标记（例如模块级 `let errorHandled = false`，catch 开头置 true、error 事件开头检查并 reset），或统一由 `error` 事件驱动重试、catch 只负责「autoplay 被策略阻止」这一种特殊分支（133 行已判 `notallowed`，可直接 return，不再走 markSourceFailed/retry）。
- 适用端：移动端（WebView / Web）。

## Bug 47 | useVideoSession.selectPart / load 无竞态 token，快速切分 P 或切 MV 时旧 IPC 响应覆盖新 src

- 现象：`src/player-video/useVideoSession.ts:93-115`（selectPart）与 `:117-143`（load）都直接 `await call(...)` 后写 `src.value = r.url` / `info.value = ...`，没有任何「本次 await 是否仍对应当前 part/bvid」的校验。
  - 快速切分 P：用户在 A 分 P 的 `music:mvurl` 未返回时切到 B，A 的响应若更晚到，103 行 `src.value = r.url` 会把 B 的 src 覆盖成 A 的流。
  - 快速切 MV（路由复用组件）：124 行 `info.value = await call('music:mvinfo', { bvid })` 同理，旧 bvid 的 info 会覆盖新 bvid 的 info。
- 影响：MV 页偶发「点了 P2 却在播 P1」「切到下一首歌但标题还是上一首」，且没有报错，难复现。
- 解决方案：在 `useVideoSession` 闭包里维护 `let reqToken = 0`，每次 `selectPart` / `load` 开头 `const t = ++reqToken`，await 之后 `if (t !== reqToken) return` 再写 src/info；或用 `AbortController` 思路在 call 层支持取消。
- 适用端：桌面 + 移动端 MV 页。

## Bug 48 | ui store `patch()` 先本地写设置再发 IPC，失败时不回滚，UI 与主进程持久化不一致

- 现象：`src/stores/ui.ts:157-165`：
  ```ts
  settings.value = { ...settings.value, ...p }   // 158 乐观更新
  apply()
  try {
    settings.value = await call<AppSettings>('settings:set', p)   // 161
  } catch (e) {
    toast(`保存设置失败：${e.message}`, 'error')   // 163 只 toast，不回滚
  }
  ```
  IPC 失败时 `settings.value` 仍是新值，主进程 DB 仍是旧值，且没有 `settings:changed` 事件把它拉回。
- 影响：用户在「弹幕开关」「桌面歌词」「下载目录」等设置页改动后，若磁盘/主进程异常，UI 显示已开启，但下次重启或主进程重连后设置丢失；DanmakuLayer、EqPanel 等读 `ui.settings` 的组件会按错误状态运行。
- 解决方案：先 `const old = settings.value`，catch 中 `settings.value = old` 并重新 `apply()`；或改成「先 call 成功再写本地」（代价是控件短暂无响应）。
- 适用端：桌面 + 移动端（共享 store）。

## Bug 49 | mobile/player.ts `load()` 中 `await resolveUrl()` 无超时，弱网/死链时 status 永久卡在 'loading'

- 现象：`src/mobile/player.ts:117-119`：
  ```ts
  const r = await resolveUrl(song, getSettings().quality, ...)
  if (index !== i) return
  ```
  `resolveUrl` 来自 `electron/core/music-service`，内部是多平台取链 + 自动换源，但没有外层超时。若某个平台 fetch 挂起（TCP 半开），Promise 永不 settle，`load()` 既不进 catch 也不返回，112 行设置的 `status = 'loading'` 一直保持。
- 影响：WebView 真机在弱网下偶发「点了歌后转圈无限，切歌/暂停按钮全部无响应」，因为 `next()`/`prev()` 虽然能发起新 load，但旧 load 残留的 await 链会在恢复后反过来 `publish()` 一次旧状态。
- 解决方案：用 `Promise.race([resolveUrl(...), new Promise((_, rej) => setTimeout(() => rej(new Error('取链超时')), 10000))])` 包一层；超时走与普通失败相同的 `markSourceFailed` + 换源/跳下一首路径。
- 适用端：移动端。

## Bug 50 | stores/player.ts `seekTo()` 乐观更新位置，IPC 失败时在 paused 状态下没有 tick 校正，UI 进度与音频实际位置脱节

- 现象：`src/stores/player.ts:256-263`：
  ```ts
  function seekTo(sec: number): void {
    syncPosition(sec)                       // 257 本地立即跳到 sec
    try { await call('player:seek', { time: sec }) }
    catch { /* 静默失败，下一次 tick 会校正 */ }   // 261
  }
  ```
  注释假设「下一次 tick 会校正」，但 paused 状态下主进程根本不发 `player:tick`（tick 由播放中的 media element 驱动），257 行的乐观位置就永远停留在用户拖动的值。
- 影响：用户暂停后拖进度条，主进程 `player:seek` 若因任何原因失败（IPC 抖动、主进程未就绪），UI 显示新位置，但下次按播放时音频从旧位置开始； LyricsPane 高亮行也与实际声音错位。
- 解决方案：catch 中主动 `const s = await call<PlayerState>('player:state'); applyState(s)` 回拉一次；或 seekTo 不做乐观更新，等 IPC 返回后再 `syncPosition`（配合 ProgressBar 自身的拖拽态可以掩盖延迟）。
- 适用端：桌面（Electron 主进程播放器）。

## Bug 51 | stores/player.ts `setVolume()` 乐观更新音量，IPC 失败时静默，音量条与实际输出不一致

- 现象：`src/stores/player.ts:265-272`：
  ```ts
  async function setVolume(v: number): Promise<void> {
    state.value.volume = v          // 266 立即本地更新
    try { await call('player:volume', { volume: v }) }
    catch { /* ignore */ }          // 270 静默
  }
  ```
- 影响：与 Bug 50 同类。用户拖音量条后，若主进程 `player:volume` handler 抛错（例如 AudioContext 被挂起），UI 音量已到 80%，实际输出仍是旧值；用户以为没生效会继续拖，最终 UI 与实际差距越拉越大。
- 解决方案：catch 中回滚 `state.value.volume = oldVolume`，或从主进程重拉状态。
- 适用端：桌面。

## Bug 52 | player-core/state.ts 的 `PlayStatus` 联合类型缺少 `'stopped'`，与 mobile/player.ts 运行时写入的 `'stopped'` 不一致

- 现象：
  - `src/player-core/state.ts:9`：`export type PlayStatus = 'idle' | 'loading' | 'playing' | 'paused' | 'error'`
  - `src/mobile/player.ts:183`：order 模式播完时 `status = 'stopped'; publish(); return`
  - `src/mobile/player.ts:412`：`clearQueue()` 中 `status = 'stopped'`
  - mobile 端 `status` 变量类型标注为 `PlayerState['status']`（`@shared/types`），但 `coreState` 用的是 `PlayStatus`，两者无交叉；任何在 `player-core` 层做 status 分支判断的代码（例如 `if (st === 'stopped')`）在 TS 层面会被认为是「永不成立」而被优化掉或在 lint 中报错。
- 影响：未来若在 `player-core` 加「stopped 时隐藏 MiniPlayer / 重置封面」之类的逻辑，写法不上去；且桌面与移动端对「播完」的语义不统一（桌面用 'idle'，移动用 'stopped'），跨端组件难以复用。
- 解决方案：在 `PlayStatus` 中补 `| 'stopped'`，并在 `CorePlaybackState.status` 注释中说明移动端 order 播完 / clearQueue 会进入此态；或反过来 mobile 端统一用 `'idle'` 代替 `'stopped'`（推荐后者，与桌面对齐）。
- 适用端：两端（类型定义层）。

## Bug 53 | mobile/player.ts `next()` 在 shuffle 模式下不排除当前 index，可能连续随机到同一首

- 现象：`src/mobile/player.ts:173-187`：
  ```ts
  if (mode === 'shuffle') {
    void load(Math.floor(Math.random() * queue.length), true)
    return
  }
  ```
  没有排除 `index`，队列较短时（例如本地音乐只有 3 首）连续两次随机到同一首的概率达 33%。
- 影响：随机播放体验像「单曲循环」，用户会以为 shuffle 失效。
- 解决方案：`let ni = index; while (queue.length > 1 && ni === index) ni = Math.floor(Math.random() * queue.length); void load(ni, true)`；或维护一个未播集合，播完再重洗。
- 适用端：移动端（桌面主进程 shuffle 逻辑未在本轮取证范围，需对照 electron 主进程实现确认是否同问题）。

## Bug 54 | mobile/player.ts `setQuality()` 触发的 `load()` 无请求 token，快速切音质时旧音质的 resolveUrl 响应可能后返回并覆盖 el.src

- 现象：`src/mobile/player.ts:348-354`：
  ```ts
  setQuality(q: string): PlayerState {
    saveSettings({ quality: q as any })
    if (index >= 0 && !el.paused) void load(index, true)   // 351
    else publish()
    return state()
  }
  ```
  `load()` 内部仅在 119 行用 `index !== i` 判断是否切歌，但 `setQuality` 不改变 `index`，所以快速切两次音质时，两次 `load(0, true)` 并行 await 各自的 `resolveUrl`：先返回的旧音质 URL 会被后返回的新音质 URL 覆盖（反之亦然）。若旧音质 resolveUrl 更慢，用户明明切到「320k」，最终 el.src 却是之前选中的「flac」流。
- 影响：音质切换偶发不生效，且无任何报错；配合 Bug 49 无超时，弱网下概率更高。
- 解决方案：在 `load()` 中引入局部 token（类似 `lyricToken`）：`const myToken = ++loadToken;` await resolveUrl 之后 `if (myToken !== loadToken || index !== i) return`，再写 `el.src`。同样的 token 机制可一并解决 Bug 46/49 的残留异步写回问题。
- 适用端：移动端。
