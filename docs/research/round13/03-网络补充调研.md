## 二、开源官方治理策略摘录

### 2.1 LX Music（落雪音乐）— 官方仓库不含音源 + 音源协议外置

**核心策略（已查证）**：
- 官方立场：软件本体不带曲库，"刚装好的洛雪音乐助手界面空白、搜索没有结果，并不是安装失败，而是还没有完成音源配置"（https://lxmusic.ijinshan.com/ ）。
- FAQ 官方原文（2023-10-18 起因腾讯投诉）："桌面版 v2.6.0 移除了所有内置自定义源，且旧版本内置的源也已失效。你需要编写或寻找别人分享的自定义源导入，才可正常使用。"（https://lxmusic.toside.cn/desktop/faq/cannot-play-and-download ）
- 许可协议补充条款中对"官方音乐平台"（酷我/酷狗/咪咕等）与"版权数据"做专门词语约定，作为 Apache 2.0 之外的合规补充（https://lxmusic.toside.cn/mobile/license ）。

**音源协议要点（已查证，https://lxmusic.toside.cn/mobile/custom-source ）**：
- 音源即 JS 脚本，UTF-8，ES6+，头部注释声明 `@name / @description / @version / @author / @homepage`；
- 通信为事件制：`inited`（上报支持的源与音质）/ `request`（宿主请求 musicUrl/lyric/pic，回调必须返回 Promise）/ `updateAlert`（源主动弹窗提示用户更新源，附 updateUrl）；
- 源 key 固定枚举 `kw/kg/tx/wy/mg/local`（酷我/酷狗/腾讯/网易/咪咕/本地），音质枚举 `128k/320k/flac/flac24bit`；
- 宿主暴露受限能力集：`lx.request`（不受跨域限制的 HTTP）、`lx.utils.crypto`（md5/aes/rsa）、`lx.utils.buffer`；运行在轻量 JS 引擎中，**浏览器/Node 环境 API 不可用**，且禁止改原型链（仅允许扩展自定义方法），即沙箱化。

**启示**：落雪把"播放器本体"与"音源"彻底解耦，音源是带版本号、可作者自推送更新提示（updateAlert）、运行在受限沙箱里的第三方脚本——这是星河可直接对标的治理骨架。

### 2.2 MusicFree — WASM 插件协议 + 注册表订阅 + 错误码治理

**核心策略（已查证，https://ansgoo.github.io/music-free-site/plugin-development.html ）**：
- 插件形态：基于 Extism WASI **WASM 沙箱**，必需 `manifest.json` + `entry.wasmPath` 指向的 `.wasm`；
- 协议版本号：`apiVersion = "musicfree.plugin.scraper.v1"`，入出参一律 UTF-8 JSON，统一信封 `{ok:true,data:{...}}` / `{ok:false,error:{code,message,retryable,details}}`；
- **错误码体系**（直接可抄）：`no_match`（无结果，不可重试）、`invalid_config`、`invalid_request`、`rate_limited`（限流/429，**建议 retryable:true**）、`network`、`timeout`、`internal`；
- 运行时权限：HTTP 请求由**宿主统一注入/管控出站**，插件只能访问 `/coverArt` 与 `/cache` 两个映射目录；禁止 `..` 路径穿越；封面必须落盘后返回 `sha256-<hex>.ext` 文件名，禁止用 http URL 冒充本地文件；
- 注册表：插件发布到 npm/GitHub/自托管后合入公共注册表（如 `https://cdn.jsdelivr.net/npm/musicfree-plugin@latest/artifact/registry.json`），宿主订阅注册表扩充插件商店（https://ansgoo.github.io/music-free-site/plugin-collection.html ）；
- 调试：插件诊断日志写 stderr，宿主 `logging.capture_plugin_wasi` 开启后汇入统一日志。

**启示**：MusicFree 的「错误码 + retryable 标记 + 宿主管控 HTTP + 注册表订阅」是比落雪 JS 脚本更严格的现代治理范式，星河的插件/音源 SDK 应对齐这套错误语义。

## 三、工程实践建议（基于上述证据归纳）

### 3.1 音源失效应对：降级 / 换源 / 提示 / 灰度

1. **多源并发搜索 + 单源异常隔离**（已查证，https://juejin.cn/post/7582857981894459433 ）：
   - 各源并发搜索、流式返回（谁先返回谁先展示），以 `sourceCode_id` 去重；
   - 每个源 `try/catch` 独立包裹，单源异常记日志并跳过，**不得让一个源拖垮全局搜索**；
   - 该方案实测播放成功率从 60% → 90%+，单源失败概率 10-20% 时整体仍 90%+。
2. **播放失败自动换源**（已查证同上）：`onPlayerError` 弹"当前源播放失败，是否尝试其他源？"，实测自动切源成功率 70%+。
3. **断流续播**（一方称，https://newreleases.io/project/github/sproft/ytmusic-free-provider/release/v1.2.1 ）：流 URL 中途停止时，重新解析同曲新地址，**先校验新旧地址是同一文件**再从断点字节续播，避免跳曲/重播。
4. **null/空值容错**：解析返回 null 时降级为空列表 + 空状态 UI，不崩不白屏（实测容错率 95%+）。
5. **按平台粒度摘除**（案例 2 的直接启示）：投诉针对单一平台时，星河应能远程禁用该平台音源而保留其余——音源配置中心必须支持"按源 key 灰度关闭 + 公告文案下发"。
6. **错误码语义对齐 MusicFree**：`no_match`（正常无结果，不打扰用户）vs `rate_limited`（retryable，可退避重试）vs `invalid_config`（提示用户配置）vs `network/timeout`（提示检查网络）——不要把所有失败都抛成同一句"播放失败"。

### 3.2 监控与调试

1. **音源请求日志统一归口**（参照 MusicFree）：插件/音源层 stderr/诊断日志汇入宿主统一日志，问题定位靠日志不靠用户口述。
2. **用户反馈通道 = GitHub Issues + FAQ 文档化**（已查证，https://lxmusic.toside.cn/report ）：落雪把高频失效场景（代理设置拦截、光猫需断电重连、音频输出设备为空）写成 FAQ 条目，大幅降低 issue 重复量；星河应在设置页内置"音源状态/一键导出诊断日志"。
3. **源健康检查**：参照社区音源仓库 issue 模式（IP 被封、产物残缺 KB 级），星河可定期轻量探测每个音源的 search+musicUrl 通路，失败时在 UI 标灰并提示"该源可能失效"。
4. **版本探测与公告**：音源脚本带 `@version`，对端接口升级时作者可通过 updateAlert 类机制主动推更新提示；星河服务端保留"音源下线公告"下发通道（案例 6 公共 demo API 过期的教训）。

### 3.3 合规红线（案例 1/2/4/5 的共同结论）

- 不内置"破解/盗链"逻辑，音源解析外置为可插拔插件/用户自填后端；
- 不共享/依赖他人 VIP cookie；
- 保留按平台粒度远程摘除音源的能力；
- 用户协议中对齐各平台"禁止第三方工具"条款的免责边界（参照 QQ 音乐/网易云音乐服务条款表述）。
