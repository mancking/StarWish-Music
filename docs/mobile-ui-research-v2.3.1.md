# 移动端 UI 独立设计调研与决策（v2.3.1）

> 背景：2.3.0 真机测试反馈「UI 还是移植桌面端」。本文档先调研、后评判、再落地，
> 作为移动端 UI 的设计基线；后续各端 UI 迭代均须遵循「同源不同形」原则。

## 一、调研：主流移动音乐 App 的交互范式

对网易云音乐、QQ音乐、Spotify、Apple Music 的移动端共性模式归纳：

| 模式 | 具体表现 | 与桌面端的本质差异 |
| --- | --- | --- |
| 底部一级导航 | 4~5 个 tab（推荐/发现/视频/我的），拇指热区 | 桌面为左侧栏树形导航，信息密度优先 |
| 分区卡片流 | 首页按「每日推荐→歌单→排行榜→场景」分区，**横向滑动卡片流**（snap 滚动） | 桌面为多列网格，一眼尽量多内容；移动为单列分区+横滑 |
| 沉浸播放页 | 全屏、封面主导、歌词跟随、上下滑切歌/下滑收起 | 桌面为半屏播放面板/独立窗口 |
| 底部悬浮迷你条 | 全局常驻、点击展开播放页、常带进度条 | 桌面为底栏 MiniBar，逻辑相同但布局不同 |
| 大触控目标 | 可点区域 ≥44dp，列表行高更大 | 桌面 28~32px 行高，依赖 hover |
| 底部动作面板 | 歌曲操作用 bottom-sheet 弹出，而非 hover 菜单 | 桌面右键/悬停菜单 |
| 手势体系 | 边缘右滑返回、下拉刷新、卡片横滑 | 桌面依赖快捷键与滚轮 |
| 引擎宽容度 | 兼容 3~5 年前的系统 WebView，渐进增强 | 桌面 Chromium 随 Electron 打包，版本恒定 |

## 二、评判：v2.3.0 移动端的问题定位

1. **布局骨架已经独立**（TabBar/MiniPlayer/沉浸播放页均为移动端专属实现），但
   **内容层仍是桌面网格**：Home/Discover/搜索/榜单在窄屏下直接压缩桌面栅格，
   出现 3~4 列小卡片、字小、误触，是「移植感」的主要来源。
2. **歌曲操作沿用桌面菜单**：SongList 的操作菜单是桌面 hover/右键形态，
   触屏上触发困难。
3. **手势残缺**：播放页已有手势，但全局边缘返回缺失；下拉刷新绑定错容器
   （`.content` vs `.m-content`）等于没有；部分老设备 WebView 引擎过旧，
   `color-mix`/`100dvh`/PointerEvent 静默失效，表现为「手势坏了/样式坏了」，
   需要引擎检测与升级引导弹窗。
4. **启动观感差**：mount 前串行等全部初始化，白屏时间长。

## 三、决策（v2.3.1 落地范围）

- **D1 分区卡片流首页/发现页**：≤600px 视口下，网格改单列分区 + 横向 snap 卡片流，
  卡片 ≥120px 宽、标题 13px 以上（mobile.css 媒体查询实现，不动桌面样式）。
- **D2 触控目标**：列表行高、按钮热区在移动端提升到 ≥44px。
- **D3 手势补全**：全局左缘右滑返回（跟手指示条）、迷你条上滑展开播放页、
  下拉刷新修绑定并改「松手即刷」。
- **D4 引擎升级引导弹窗**：启动检测 WebView Chrome 内核版本，
  <100 时弹窗说明并引导跳应用商店升级（市场链接 + 复制链接兜底）。
- **D5 启动**：mount 提前、仓库初始化后台化、boot 内部并行化。
- **D6 系统能力**：MediaSession 锁屏控制、应用内下载安装更新包（不跳浏览器）、
  外链用系统浏览器打开。
- **暂不做**（记录为后续版本）：歌曲操作 bottom-sheet（涉及 SongList 重构）、
  原生下载到本地（需存储权限与 MediaStore 接入）、平板双栏。

## 四、验收口径

- 与桌面端对比：同一路由在两端布局/交互无同构呈现。
- 触控目标、横滑卡片、边缘返回、下拉刷新在真机可用。
- 老引擎设备能收到明确的升级引导，而不是静默坏样式。
